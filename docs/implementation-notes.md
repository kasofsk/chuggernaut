# Implementation notes — rationale hoisted out of comments

**Audience:** anyone changing the modules listed below. This page is the
**rationale archive**: when job #342 deleted every non-doc comment in the tree
(docs/reference/style.md Tier 1, `.chug/tasks/check-comments.sh`), the explanations that were
load-bearing landed here rather than in `git log`.

Read it as *notes about a module*, not as a specification. Normative behavior
lives in [`docs/spec.md`](spec.md); the arguments behind a decision live in
[`docs/design/000-rationale.md`](design/000-rationale.md) and [`docs/design/`](./design/); the contract of a
module lives in its `//!` header and its [`docs/reference/modules.md`](reference/modules.md) row.
Where this page and any of those disagree, they win and the entry here is
stale.

## How to use it

- Entries are grouped by source file and, inside a file, tagged with the item
  (`fn`, `struct`, `impl`, `const`) the note sat next to when it was a comment.
  Items move; the tag is a hint for finding the code, not an anchor.
- **Folding an entry into a better home is the point.** A note that belongs in
  `docs/spec.md`, in a design document, in a module `//!` header or in a two-sentence
  doc comment should be moved there by the next `docs` job that touches the
  area, and deleted from here.
- What is *not* here: notes from test files and `#[cfg(test)]` modules (a test's
  name carries what its comment said — `docs/reference/testing.md`), and one-line comments that
  only restated the code beneath them. The full pre-strip text of every deleted
  comment is in git history, at the commit before job #342.

## The notes

### `crates/agent/src/claude.rs`
- **fn run** — Hand the id back before we block on the container's exit, so the task record carries it while Running (#71/#72).
- **fn run** — The provider owns the timeout for its own container (§3.5's scan has historically had no id for agent tasks). A timeout still returns Ok: the container is killed, but the caller must be handed the id so it can harvest the transcript — a timed-out run is the one most worth reading. Exit -1 marks it, matching the dispatcher's failure encoding.
- **fn parse_permission_denials** — Bash is the interesting case — the command is what tells an operator whether the profile is wrong or the agent was.
- **fn settings_json** — As permissive as the bypass flag it replaces — work agents edit, build, commit and push. Only the shape is new.
- **fn settings_json** — Reading the change under review. `git diff`/`log`/`show` are what .chug/tasks/review-*.md actually ask for. The task container clones `--single-branch` (crates/container), so the base ref is absent until fetched — `git fetch`/`merge-base`/`rev-parse` are what make the prompts' `git diff $BASE_BRANCH...HEAD` resolve at all, and none of them build or mutate the worktree.

### `crates/api/src/lib.rs`
- **fn router** — Operator capacity control (§3.1): the desired slot count for one worker node. 202 — the dispatcher records intent and converges.
- **fn router** — Artifacts (§4.2): transcripts and container logs Live/paged container output for a running task, falling back to the harvested stdout.log artifact after exit (§4.2)
- **fn router** — Raise the body cap above axum's 2MB default so a screenshot upload is not rejected before the handler runs.
- **fn router** — Vite content-hashes everything under /assets, so a given URL's bytes never change — cache it forever and skip even the revalidation RTT. Everything else (index.html, sw.js, the manifest, icons) keeps the default no-cache behavior: those URLs are stable across builds, so a long TTL would pin operators to a stale shell.
- **fn router** — Compress every response the client will take it on. The default predicate already skips SSE (`text/event-stream`), gRPC, images, and sub-32-byte bodies, so the live event stream still flushes per frame. Applied last so it wraps the static fallback too — the UI bundle is the single largest transfer the operator makes.

### `crates/api/src/oidc.rs`
- **fn public_routes** — A separate router function rather than two more rows in `router`'s chain: the api authenticates per handler (the `Auth` extractor), so a route with no extractor is unauthenticated *by omission*, and these two are unauthenticated *on purpose*. Building them here is what makes the exemption reviewable — and testable, since a test can drive that router alone.
- **fn discovery_documents** — 404, not an empty key set, when no `oidc_public.pem` is mounted: an empty JWKS is a valid document that says "this issuer signs nothing", which a consumer would cache. A platform initialized before the issuer keypair (§12.1) reads as absent rather than as an issuer with no keys.
- **fn new** — Both documents are built once at startup, so a malformed key or issuer fails the process rather than every request, and a request costs no DER walk.

### `crates/api/src/routes.rs`
- **fn from_request_parts** — `Authorization: Bearer <jwt>` first (machine callers — CLI-minted tokens, §7.1), then the browser session cookie. Same JWT either way.
- **fn health** — Only a genuine {"dispatcher":"ok",..} reply is healthy; anything else (e.g. the actor's 503 envelope) maps to 503, never 200.
- **fn ssh_cert** — The dispatcher loads the caller's roles from their user record and signs; we forward only the authenticated email, never a client-supplied identity.
- **fn project_config_get** — secrets — NAMES ONLY (the api holds no decryption key). Split the reserved origin credentials out into presence flags.
- **fn platform_fleet_get** — Served verbatim rather than re-serialized through `types::FleetStatus`. The api and the dispatcher deploy at different moments (the reason `api_sha` exists at all), so a typed round-trip here would silently drop the per-node capacity fields a *newer* dispatcher writes — a capacity path failing invisibly, which is the exact class of failure design #293 exists to remove. This crate is a bridge and reads none of these fields.
- **fn platform_fleet_get** — Cold start: the dispatcher has published nothing yet. An empty fleet, never a 404, so the UI needn't special-case it.
- **fn diff** — Live task output (§4.2): cursor-paged container stdout/stderr A running task's container is tailed live via the dispatcher (a bounded req/reply, no held-open stream through the core actor); once it exits, this falls back to the harvested `stdout.log` artifact at the SAME byte offsets, so a poller never loses the tail when the container is removed (job #10).
- **fn task_output** — The dispatcher signals errors (404 no container yet, 502 wedged node) in the §6.5 envelope — propagate its status verbatim.
- **fn task_output** — Finished (or the container is already gone): serve the harvested stdout.log from `since` on, so a poller that had offset N off the live stream continues seamlessly into the artifact.
- **fn task_output** — No artifact store configured: the task is finished with nothing to replay. Hold the cursor so a poller sees `running: false` and stops.
- **fn task_output** — Artifacts (§4.2): session transcripts and container logs These stream from the object store rather than riding a req/reply through the dispatcher: a transcript routinely exceeds NATS's 1MB max_payload, which a reply cannot carry. Decryption happens here because the API holds the `age_artifacts` identity — a separate key from the secrets one, which stays dispatcher-only (§10.2).
- **fn artifacts_list** — Job attachments (§1.6): operator-uploaded files Screenshots on a bug report, reference documents. Like transcripts, these stream directly from the object store rather than riding a req/reply through the dispatcher — a screenshot routinely exceeds NATS's 1MB max_payload — and the API encrypts on upload / decrypts on download with the `age_artifacts` identity it already holds. Presentational reference material: never injected into an agent prompt.

### `crates/api/src/run.rs`
- **fn run** — The artifacts identity — not `age_private.key`, which stays dispatcher-only (§10.2). Missing → the platform captures no artifacts, and the routes report that rather than failing startup.
- **fn run** — The issuer public key is optional the same way, but `OIDC_ISSUER` is validated unconditionally in `from_env`: a malformed issuer is a config error whether or not a key is mounted today, and the §6.7 documents are worth nothing if the string in them is not the one a provider was registered with.

### `crates/api/src/sse.rs`
- **fn project_events** — A fresh connect gets live events only. The project feed spans every job the project has ever run, so replaying it costs the operator a multi- megabyte download before the first live frame — and nothing needs it: the page's initial state comes from the jobs list (which now carries each live job's latest channel post), and this stream's job is to keep that state current. A reconnect still resumes exactly where it left off.
- **fn job_events** — Unlike the project feed, one job's history is bounded and *is* the content: the detail page renders the event log itself. Replay it whole.

### `crates/auth/src/nats.rs`
- **fn resolver_config** — §7.4 allow-lists, mapped to the concrete NATS subjects behind each KV and stream operation the injected binaries perform (KV get = JetStream direct get; channel_check = ephemeral pull consumer on `channel-inbox`).
- **fn common_container** — Deliberately no `kv_write` on CHANNELS: containers post through the dispatcher instead, keeping it the sole writer of the bucket and making each post durable event history rather than a last-write-wins overwrite.
- **fn common_container** — Knowledge keys nest b64 segments (`global.{s}.{p}`, `{owner}.{s}.{p}`, `{owner}.{project}.{s}.{p}`): `{owner}.>` covers the §7.4 owner and project grants in one pattern.
- **fn common_container** — channel_check: ephemeral pull consumer on the inbox stream. Unnamed ephemeral creation targets `CONSUMER.CREATE.{stream}` exactly (no trailing tokens, which `.>` would require), named/filtered creation appends `.{name}.{filter}`.

### `crates/auth/src/oidc.rs`
- **fn kid_from_public_pem** — The RFC 7638 JWK thumbprint rather than a digest of the raw SubjectPublicKeyInfo: both are stable functions of the key, but only the thumbprint is reproducible by a JWKS consumer holding the published JWK, and that consumer is the party that has to agree with us about the id. The DER walk is hand-rolled because the only members a JWK needs are `n` and `e` out of a fixed SPKI shape, and nothing in the tree parses them — a DER/ASN.1 dependency would be a large supply-chain edge for ~25 lines.
- **fn resolve_issuer** — Configuration rather than a constant, and one resolver rather than one per process: the issuer is the single value the api's discovery document and the dispatcher's minted `iss` must agree on byte-for-byte, and a disagreement is invisible here and fatal at a cloud STS. The validation is strict (absolute `https`, no trailing slash) because every way of being loose about it fails there instead, under an error message that names the issuer whatever the real fault was.

### `crates/auth/src/ssh.rs`
- **fn authorize_ref_push** — A platform admin (§7.3) pushes to any job branch in any project, but the default branch stays dispatcher-only for everyone.

### `crates/auth/src/workload.rs`
- **mod workload** — In `auth` rather than `chuggernaut-domain` (design #313 S2 left the choice open): a mint is a credential construction, not a lifecycle decision. It needs the issuer key and `jsonwebtoken`, and the pure core resolves neither by construction (`boundary_guard`'s `domain_subtree_is_sync` forbids the `auth` edge outright), so putting it there would mean either widening that crate's dependency floor or splitting the claim set from the token it exists to produce. The decision it sits beside — *which* identities a container is granted — is the part that stays on the decider side, in #313 S3/S4. It is also where the `kid` lives (`oidc`, next door) and where §7.4's other two per-task credentials are already minted (`nats`, `ssh`).
- **struct WorkloadTokenRequest** — Typed fields are the injection defense, not a validation rule bolted on after: with no free-text field on the request there is nothing for a CEL expression to be injected through, which is #311 Decision 5's argument applied to a claim. The charset floor (`types::inputs::check_value_charset`) is a second, cheaper line — reused rather than re-stated so the two cannot drift.
- **fn check_component** — `:` and `/` are refused in `owner`, `project`, `job_type` and an evaluator name because both composites join on them; without the rule a project literally named `x:type:deploy` could make one `sub` read as another. The audience and the issuer are exempt: they are full resource names and URLs, and neither is a component of a composite.
- **const PROVIDER_TTL_SECS_MAX** — A configured cap above the provider's 24h `exp − iat` ceiling is refused rather than clamped: clamping would hide a job type asking for something the provider will not honor, and the resolved TTL is already `min(task_timeout, cap)` so a large *timeout* clamps quietly and correctly. That asymmetry is deliberate — a timeout is the job's, the cap is the operator's.
- **struct MintedWorkloadToken** — The hand-written `Debug` and the absence of `Display`/`Serialize` on the token are §10.2 made structural: `{minted:?}` in a future log line cannot leak the credential, and the audit row (`identity`/`audience`/`sub`/`workload`/`jti`/`expires_at`) is a separate value precisely so the recording path never holds the token at all.

### `crates/cli/src/keygen.rs`
- **fn ensure_all** — SSH CA (§7.4) — ssh-keygen writes both halves in one shot, so report the .pub as generated too rather than "skipped".
- **fn ensure_all** — Artifacts (transcripts, container logs) — a *separate* age keypair from the secrets one above. §10.2 keeps the secrets identity dispatcher-only, but the API must decrypt artifacts to serve them, and proxying blobs through the dispatcher would reintroduce the NATS max_payload cap that the object store exists to avoid. Every consumer is handed `KEYS_DIR` whole — the prod/dev compose files bind-mount the directory, `run-api.sh` and `run-dispatcher.sh` export it, and `deploy/backup.sh` copies it with `cp -Rp` — which is why `age_artifacts.key` appears in neither tree either. The split between "dispatcher-only" and "also the api" is enforced by which process *reads* which file, not by the mount.
- **fn ensure_all** — NATS decentralized auth (§7.4): operator + system + platform account nkey seeds, generated in-process (nkeys is already in the tree via the NATS client). Derived server/dispatcher artifacts: ensure_nats_artifacts.

### `crates/container/src/lib.rs`
- **fn choose_placement** — Unpinned, the postcondition is: the winning in-service node under `policy` among the candidates that serve the required mode. Out-of-service (`load: None`) and full/0-slot (`free <= 0`) nodes are never chosen — the #60 rule holds under both policies — and `NoCapacity("no free slots on any node")` is the answer when none is eligible (transient: the dispatcher queues and retries, spec §3.5).
- **fn choose_placement** — Pinned, it is the named node or an error, never a fallback: an out-of-service pin, or a full pin onto a node that *does* serve the mode, yields the same `NoCapacity` "no free slots" shape as the unpinned case; an unknown pin is a hard `Launch` error naming the known nodes; and a pin onto an in-service node that does not serve the required mode is a hard `Launch` error whether or not that node has a free slot (design #309 §5a, and [the slice-6 note](design/309-host-native-execution.md#note-2026-08-07--slice-6-landed-host-work-is-routable-job-484) for why that one is not transient).
- **fn choose_placement** — So on the pinned path the capability verdict is reached after the out-of-service check and *before* the free-slot one: a node that has answered no probe advertises nothing and is still booting, while a full incapable node's live answer is already final and waiting out its slot would only reach the same hard error.
- **fn choose_placement** — On the unpinned path the fleet-wide capability check runs before any free-slot or out-of-service test, so "no node advertises this mode" and "every capable node is full" stay distinguishable; an empty candidate set is the second, because zero nodes is spec §3.1's zero-seed boot rather than a fleet refusing the mode.
- **fn choose_placement** — The design #309 §7 resource requirement rides the same filter rather than a second code path: a launch declaring `resources.cpu`/`memory` is judged exactly as a mode requirement is, one fleet-wide check ahead of the per-candidate loop and one clause inside it. Its fleet-wide answer is deliberately `NoCapacity` and not a hard error — §7 wants the common case queued and transparent — while the pinned case is `Launch`, for the same reason the mode pin is: a pin never falls back, so waiting cannot clear it.
- **fn choose_placement** — The design #543 D2 environment requirement rides that same filter for the same reason, and its refusals follow the mode precedent exactly: `NoCapacity` naming the reference and every node's advertisement when nothing in the fleet serves it, a hard `Launch` naming the reference and that node's set when a pin does not. It sits after the mode verdict on both paths, because a node that cannot run the mode has nothing to say about the environment, and before the limits one, because an environment is the coarser statement of the two.
- **fn serves_env** — Only the **node-interpreted** half of a launch's `runtime.env` is a placement input (`types::job_type::env_is_node_advertised`), and that predicate is the `xcode:` scheme rather than "not `nix:`". `NodeCapabilities.envs` is built from the discovered Xcode set alone, so a reference in a scheme no node advertises would otherwise match against a set nothing ever puts it in and queue forever — where today the node refuses it by name at launch (`unservable_scheme`). The mirror cost is real and deliberate: a scheme added to the node's resolver and to `envs` but not to this predicate is placed unfiltered, exactly as before the filter existed. Neither refusal prescribes "install it": `Xcodes::envs` withholds a version **two** bundles claim, so an unadvertised reference is absent on the node or ambiguous there, and the node's own resolution refusal is the one that names which.
- **fn bounds** — Enforceability is a property of the launch's **resolved mode**, not of the node (job #524, the shape #507 found for `runtime.env` and #517 D4 for docker access). `NodeCapabilities.resources_enforced` is derived from container capability, so a dual-mode node's `true` answers for the launches its Docker `HostConfig` bounds and never for the host ones it also takes — narrowing the advertisement instead would have made `gumbo-air-0` refuse the ten container job types in this repo that declare limits, which is a fleet change and not a fix.
- **fn unenforceable_limits** — One message for the placement filter's pinned case and `HostBackend::admit`'s backstop, because they are the same refusal reached two ways and a drifted pair would read as two rules. It names the field and the node: §7 rejected option 1 (enforce where possible, advisory elsewhere) precisely because a bound that silently does nothing on one node and OOM-kills on another makes behaviour depend on invisible placement.
- **fn bootstrap_cmd** — Images must provide `git` and an SSH client but never clone themselves; the platform owns the workspace contract. `--single-branch` skips every other in-flight `job/*` and `merge-gate/*` ref — the container only ever works on its own branch and all merging is server-side, and without it each task also drags in every concurrent job's unmerged work. `--filter=blob:none` skips historical blobs while keeping the commit graph, so `git log`/`git blame` still work as agent context.
- **fn bootstrap_cmd** — Both flags depend on server-side setup and both fail *silently-ish* without it: `uploadpack.allowFilter` on the bare repo (`RepoManager::create_project`), else the filter is ignored and the full history ships anyway; and git protocol **v2** through the SSH front (`AcceptEnv GIT_PROTOCOL` in sshd_config), since on v0 upload-pack refuses the promisor remote's follow-up fetch for unadvertised blobs — the clone "succeeds" and checkout leaves an empty workspace. git supplies the client half itself.
- **fn bootstrap_cmd** — `git config core.hooksPath .githooks` runs after the clone, inside /workspace, so the hook the agent commits under is the one its own branch carries (a baked-in hook could only change with a worker image rebuild, and would skew from the code it checks). Project-agnostic: a repo without `.githooks/` gets no hooks and nothing happens.
- **fn bootstrap_cmd** — That step is `|| true` while the clone and `cd` stay `&&`-guarded: losing the hook degrades feedback, but exec'ing outside a clean /workspace loses the whole attempt.
- **fn bootstrap_cmd** — The destination is `${CHUG_WORKSPACE:-/workspace}` rather than a parameter, because every caller of this function is dispatcher-side and a host backend is the only thing that knows where a task's workspace really is (design #322 §2, correction 5). Unset resolves in the task's own shell to today's literal, so a container task's clone destination and cwd are unchanged and the indirection is testable at tier 1.

### `crates/container/src/host.rs`
- **fn rebase_path** — The mapping is total and unmapped is an error because a permissive one is how a `copy_file` bug becomes a write to `/` (design #322 §2). A `..` component is refused rather than resolved, which makes the containment assertion true rather than nominal; resolving **symlinks** and re-checking after normalization is W3's, and this function is where it goes.
- **fn unrebase_path** — The inverse of `rebase_path`, and total for the same reason (design #490 D1a): a host node answers `find_file` in **wire** paths, so a real path it cannot map back — outside the task directory, or under neither local prefix, which is what the task's own `meta.json` and `output.log` are — is an error rather than a node path handed to a dispatcher that would then ask for it. The mapping stays one-way *by construction* everywhere else; this is the one caller that needs the other direction, and it asserts its input rather than trusting the walk that produced it.
- **fn find_in_task** — Three bounds, because each covers what the others cannot: depth for a tree deeper than a transcript's two levels, entries for a single wide directory that depth alone leaves unbounded, and matches for the answer itself (docs/reference/style.md Tier 2 rule 3). Symlinked directories are skipped rather than followed — `file_type()` does not follow — which is also what keeps a cycle from being reachable at all.
- **fn rebase_env** — Substituting over env *values* is the ugly part of the rebase and is defensible only because both prefixes are constants this repo owns: the allowlist names the three variables that embed one (`GIT_SSH_COMMAND` inline, `GOOGLE_APPLICATION_CREDENTIALS` whole, and `CLAUDE_CONFIG_DIR` since #490 slice 5 — the tree the CLI writes its transcript into, which has to land inside the task directory for the `find_file` the harvest runs to resolve in the same tree), and a prefix that **begins a path** in any other value is refused rather than rewritten (`fn first_wire_prefix`, below, is what makes that a mention rather than a substring). A mention that continues into another path segment (`/workspaces`, `/chuggernaut-old`) is refused on the same boundary `rebase_path` requires, so a lookalike is never quietly rewritten into a path the node does not have. That refusal is the design's assertion — a third consumer interpolating a wire path fires it instead of shipping a credential that silently points at nothing. A file's *contents* are not scanned, so an injected document that names a wire path inside itself (`adc.json`'s token path) is not rebased; nothing declares `workload_identities` under host mode today.
- **fn first_wire_prefix** — A wire prefix is a **mention** only where a path can begin: at the start of the value, or after ASCII whitespace, `=`, `:` or a quote — the delimiters that end the previous token in the command lines and bare paths the three allowlisted variables actually carry (`ssh -i /chuggernaut/ssh/id`, `CertificateFile=/chuggernaut/...`, a whole path at offset 0). Every other character continues a path segment, so `/kasofsk/chuggernaut.git` and `/kasofsk/workspace.git` hold no mention at all and are neither rebased nor refused — the second is the harder case, since it does contain the prefix `/workspace` and only the left-hand boundary rejects it; a substring search with only the right-hand boundary read those as wire paths, and since `REPO_URL` is injected into every job that refused **every** host launch in this repository (job #505). The narrow accept set is the trade the refusal already makes: an occurrence the rule does not accept is passed through silently, so it is widened only for a delimiter a real value uses, never for a character a file name may contain.
- **fn substitute_wire_paths** — The scan resumes at an absolute offset in the original value rather than in a fresh suffix, because the left-hand boundary is a question about what precedes an occurrence and a suffix has lost it. That keeps the one property the fresh slice bought — a task directory whose own name holds a prefix is written to the output and never rescanned — while making the tail of a rebased path (`/workspace/chuggernaut-cache`) that path's own segment instead of a second mention.
- **fn supervised_cmd** — The wrapper empties the mapped `chuggernaut/` tree as its first act after the command returns, earlier than `remove` (design #322 §2 teardown): `logs` and `copy_file` must outlive the process, but the secrets must not. `spawn_reaper` repeats it when the daemon observes the terminal state, which covers a wrapper killed before it got there; the durable bound is still the credential's TTL, not the file's lifetime.
- **fn supervised_cmd** — It deletes the tree's entries one level down rather than the tree, sparing `AGENT_STATE_DIR` — the CLI's own config directory, which is where the transcript the harvest reads *after* the process exits lands (design #490 D6 amendment). That leaf is a harvested artifact and not an injected credential, so it takes the lifetime `logs` and `copy_file` already have: inside the 0700 task directory until `remove` reclaims the whole of it. `reclaim_credentials` spares the same leaf, or the reaper would delete it in the window between the process exiting and the harvest resolving it.
- **fn task_env** — The launch environment is composed, never inherited (design #440 slice 1): `spawn_task` clears the daemon's environment and sets three layers, in order — the floor, the dispatcher's launch env, the two exit-status paths — so a launch declaring a floor name wins, the precedence a container's env has over its image's. The floor is `PATH` and `HOME` and nothing else: the bootstrap clones with `git` and `ssh`, which #309 §9 calls machine facts on a host node (on a nix or macOS node they live on the daemon's `PATH`, in no fixed system directory), and docker gives every container a `HOME` that git, ssh, cargo and the agent harness all key per-user state off. `TMPDIR` and `LANG` are refused because a container is given neither by its image or the runtime, so setting them would be a divergence from the docker backend rather than parity; `HOSTNAME` is refused for the opposite reason — docker sets one (the container id) and a host task simply has the node's, which `hostname` answers without a variable.
- **fn task_env** — `PATH` falls back to the value docker gives a container whose image declares none, because measurement showed a cleared environment is not inert: the shell supplies its own compiled-in default, which is the undocumented version of the same hardcoding. `HOME` gets no fallback — there is no correct value to invent, and each tool's passwd-entry lookup is the honest answer.
- **fn daemon_floor** — Reads the two floor names out of the daemon's environment one at a time rather than snapshotting all of it, so the docker socket and NATS credential this slice exists to withhold are never copied into the daemon's heap on the path whose point is not passing them on. `var_os` rather than `var` because a non-UTF-8 value in the daemon's environment must degrade to the `PATH` fallback, not panic in the launch path (docs/reference/style.md Tier 1).
- **fn supervised_launch** — Each task is launched into its own transient scope, not the daemon's cgroup (design #440 D3, #309 §6): a `systemctl restart chug-worker` — which a `nixos-rebuild switch` performs — would otherwise kill every running host task, breaking spec §3.1's drain guarantee the moment the daemon stops being a container. `--scope` runs the command from `systemd-run` itself rather than handing it to pid 1, so the composed environment, the cwd and the two log fds are inherited exactly as they are without it; the scope is a cgroup change and nothing else. `--collect` reclaims the unit when the task's last process exits, so a node that runs for months does not accumulate dead scopes. The **argv is not** inherited untouched without `--expand-environment=no`: with `--scope` the substitution is `systemd-run`'s own work rather than the manager's, it collapses `$$` to `$` and replaces `${VARIABLE}` from the *client's* environment, and systemd v258 turned it on by default for scopes (job #462, which diagnoses this as design #440 D8's staging failure without running it — the fixture's `printf %s "$$"` writing a literal `$` where a pid was expected; job #466 then ran it on a 260.2 node and all thirteen passed with no skips, so the diagnosis is a measurement). The flag is systemd v254 and later, so a client too old for it fails `probe_supervision` and the node refuses `host` rather than launching a rewritten command; those same versions do not expand a scope's argv, so nothing is lost by refusing them a flag they have no use for.
- **fn spawn_task** — Scope entry is **asynchronous and the launch does not wait for it**: `systemd-run --scope` registers its own pid with the manager, waits for the start job, and execs the task only then, so for the tens of milliseconds between the fork and that job the pid is still in the daemon's own cgroup and a restart landing there would take the task with it. D3's guarantee is therefore eventual rather than immediate, and closing the window would mean blocking every launch on a bus round trip; what it does mean is that any check of a task's cgroup must poll rather than read once, which is what `supervised_cgroup` in `crates/container/tests/host_backend.rs` exists to do (job #455) — a poll bounded by `SCOPE_ENTRY` that fails naming the cgroup the pid was in instead, so a launch that was never supervised reads as that rather than as a flake.
- **fn task_path** — The `PATH` a launch composes when the config declares none, exposed because a caller staging a tool *for* a task — the tier-2 escapee fixture is the one that exists — should follow the floor rather than its own environment. The two agree today, since the floor copies the daemon's `PATH` and in a tier-2 test the daemon *is* the test process, so this is hardening against a floor that stops carrying `PATH` and against a non-UTF-8 value `daemon_floor` drops to the fallback — not the cause of design #440 D8's staging failure on `gumbo-nuc-0`, which job #462 diagnoses, unrun, as the scope client's own expansion of the task's argv — confirmed in execution by job #466.
- **fn launch_env** — The `systemd-run` client a launch runs is the task's environment plus the borrowed bus variables, named as its own function so "the launch's client carries everything the probe measured with" is a tier-1 assertion instead of a property re-derived at each call site. A launch that refused where `probe_supervision` passed would advertise `host` and then supervise nothing — the silent lie #309 §7 rejects, arrived at one layer lower than job #453's.
- **fn probe_supervision** — Measured at daemon start rather than assumed, because a node that advertised `host` and then parented its tasks to the daemon would lose them all to the next restart while still claiming the mode — the silent lie #309 §7 rejects. The probe creates one throwaway scope rather than testing for a binary or reading `/proc/1/comm`: what has to be true is that this process, with these privileges, on this bus, can create a scope. The verdict is split into `scope_verdict` so the refusal is testable on a machine with no systemd to fail against, including the case an unbounded probe would hide: `systemd-run` waits on the manager's start job, so a wedged bus expires `SYSTEMD_BOUND` and becomes a named refusal rather than a boot that hangs silently.
- **fn probe_supervision** — It runs `systemd-run` under `env_clear` plus `probe_env` — the launch's floor and, for a `--user` scope, the two variables that locate the manager's bus — because a probe and a launch that measure different environments is exactly the failure it exists to prevent, and because the client needs those two to reach a bus at all. Job #453 measured on `gumbo-nuc-0` that clearing them from the `systemd-run` invocation makes `--user` fail in *every* environment with `$DBUS_SESSION_BUS_ADDRESS and $XDG_RUNTIME_DIR not defined`: `sd-bus` reads those names and has no `/run/user/$UID/bus` fallback computed from the uid, which is what the 2026-08-06 correction assumed. A daemon holding neither is refused before the probe runs (`bus_refusal`), because there is nothing to measure and the honest answer is that no manager can be located from this process.
- **fn borrowed_bus** — Two environments are at stake and only one of them is #309 §10's: the task's, which stays the floor plus the launch config plus the exit paths, and the `systemd-run` client's, which is a bus client and gets the bus names on top. It reads them from the daemon by name, the way `daemon_floor` reads its two, rather than widening the floor — the floor is the task's and stays two names — and it borrows nothing the launch config already declares, so a declared value keeps the dispatcher's and the daemon's never overwrites it. Only `Scope(User)` borrows: the system bus is a fixed socket path, and macOS has no client at all.
- **fn shed_borrowed** — With `--scope` the task *is* `systemd-run` after the exec, so anything the client needs to find its bus would otherwise be inherited straight into the task and re-open #309 §10. The wrapper's `unset` is the ordering that separates them — bus names before the exec, gone after it — and it names only what was borrowed, so a launch that borrowed nothing sheds nothing and a declared name is never removed.
- **fn precondition** — The advice is read out of the failure rather than out of the manager, because `loginctl enable-linger` is the remedy for exactly one of the three ways a `--user` scope fails and naming it for the others costs an operator a node change that fixes nothing (job #453). A bus that could not be reached at all is the missing user manager; a manager that answered and refused — polkit, a unit that would not start — is not provisioning, and a daemon carrying neither bus variable is our environment, not the node's.
- **fn precondition** — Unreachability is keyed on `sd-bus`'s opening `Failed to connect` and never on the errno that follows it, because `No such file or directory` is both how an unreachable bus reads and how a missing binary fails to exec — and `--scope` execs the command from `systemd-run` itself, so the second is a manager that answered. Keying on the errno would hand that case `loginctl enable-linger`, which is the same wrong advice one layer down; the phrase subsumes every `sd-bus` connect failure anyway, since they all open with it.
- **fn manager_for** — The manager is chosen by the daemon's euid and never falls back between the two, because polkit answers an unprivileged `systemd-run --scope` with `Access denied … requires interactive authentication` (measured on `gumbo-nuc-0`, job #451) while `systemd-run --user --scope` is exit 0 there. A fallback would make the mechanism's identity depend on which attempt won, and the two are not equivalent: a system scope outlives every session, a user scope outlives the daemon's unit but not that user's manager. Root gets the system manager because a root daemon has no user manager to speak of — #440 D2's Linux unit runs as root, so prod gets the stronger of the two and a hand-run test suite gets the one that works.
- **fn signal_unit** — `kill` signals the process group AND the scope, at both SIGTERM and the SIGKILL escalation. D8 calls #309 §2's `setsid()` escape closed "for free" by the scope, and the scope is what makes closing it possible — but only a cgroup-addressed signal collects the escapee, since leaving a process group does not leave a cgroup. Both are sent rather than one chosen, so a node whose `systemctl` is unusable still gets the pre-#440 behavior instead of none; the group goes first because that signal cannot block, and the `systemctl` call is bounded by `SYSTEMD_BOUND` so a wedged bus cannot hold a `kill` open indefinitely.
- **fn kill_unit_args** — Factored out of `signal_unit` for the same reason `supervised_launch` is a function of its own: the D8 half is the one line the whole slice turns on, and a machine with no systemd to send the signal to can still assert what would have been sent. Without it the SIGTERM leg, the escalation leg and the argv shape would all ship unexecuted anywhere.
- **fn kill_unit_args** — It takes the manager from `TaskMeta::scope` rather than re-deriving it, because a scope in the user manager is not a unit the system `systemctl` can see: a kill addressed at the wrong manager reports "not loaded" and leaves the `setsid()` escapee running, which is D8's one failure mode wearing a success. The field is `#[serde(default)]` and absent means the system manager, so a `meta.json` written before the manager was selectable keeps its old meaning.
- **fn supervised_cmd** — The *task* records its own exit status, not the daemon. If the daemon's reaper were the authority, a `worker-refresh.sh` swap mid-task — which spec §3.1 guarantees does not interrupt in-flight work — would lose the code, and the pid-identity rule would then report a task that succeeded as `Exited { -1 }`. The reaper stays as the backstop for a wrapper that never got to write.
- **fn status** — Three sources in a fixed precedence: the written `exit_code`, then this daemon's own live set, then the pid-identity rule. The live set is what closes the window between a process dying and its status file landing; the pid rule is what covers the case the live set cannot, a daemon that restarted under a running task.
- **fn status_after_restart** — Every unknown resolves to *gone*, including an unrecorded start time and missing meta. Design #309 §2(b): reporting a dead task as running is what spec §3.6 hears as "re-attach", which hangs the task until `task_timeout` — a slow, confusing failure instead of a loud one.
- **fn remove** — Also reclaims each path the launch materialized, which `meta.json` records at launch; since #322 W2's rebase they are all inside the task directory (`chuggernaut/prompt.md`, the ssh cert, the MCP config), so the record is a list of what to delete rather than of what escaped. Nothing else on the node reclaims them, so a failure is both an `Err` and an `error!`.
- **fn sweep_agent_cache** — The subtree is located by **listing** the cache root and matching the task directory's own name, never by computing the CLI's key (design #490 D6's second amendment): the CLI slugifies the **resolved** realpath of its cwd — slice 0 measured a cwd under `/tmp` producing a key naming `/private/tmp` — so a computed name misses silently on any task root reached through a symlink, and "removed nothing" is indistinguishable from "the CLI wrote nothing". A host task directory is `TASK_PREFIX` plus two hex fields, every character alphanumeric or `-`, so it survives any character-mapping slugifier verbatim and appears inside the key; the predicate therefore depends on a token the platform itself supplies rather than on a tool's output, and it covers the multi-cwd case a single computed name misses. The asymmetry is the whole reason for the shape — a miss leaks a log tree, a false match deletes another tool's state (the node's cache also holds an actions-runner's, dated June), so a name this backend never minted is refused rather than matched loosely and only immediate children are ever touched. A cwd **outside** the task directory yields a key this predicate deliberately does not match: residue the sweep does not bound, named in the amendment rather than discovered later.
- **fn reclaim_agent_cache** — It returns `()` rather than a `Result`, which is `crates/worker/src/nix.rs`'s reaper charter written as a type: that reaper "leaks disk rather than ever failing a job", and `remove`'s opposite strictness exists for the 5–10 GB `target/` nothing else on the node reclaims (#309 §2(c)) — borrowing it for a 68K log tree would trade a bounded leak for a failed task, so an absent, unreadable or undeletable subtree is logged and skipped and can never reach `remove`'s failure list. It runs from `spawn_reaper` beside `reclaim_credentials`, the moment the wrapper exits and one that arrives whether or not the dispatcher ever calls `remove`, and again from `remove` so a daemon restarted between the two still reclaims the subtree when the task directory goes. The cache is the **daemon user's**, since a host task runs as that user and #490 D6's second amendment rejects giving one its own `HOME`; an unset `HOME` is a skip rather than an invented path, the way `task_env`'s floor refuses to invent one. A pass that matched nothing logs what it examined instead of passing in silence — a sweep that silently matches nothing is worse than no sweep, and this one is expected to match nothing on every non-agent host task.
- **fn detach_and_remove** — The task tree is renamed aside before it is deleted, because `remove_dir_all` in place races the task's own reaper. The daemon's order is kill-then-sweep, so the reaper is often still writing `exit_code` into the directory being walked, and repopulating it mid-walk fails the whole `remove` with `ENOTEMPTY` — reported as leaked disk when nothing had leaked. After the atomic rename every writer addresses a path that no longer exists, so the delete has no concurrent writer at all; a late `write_exit_code` fails with `ENOENT` and cannot resurrect the tree, since `std::fs::write` never creates a parent.
- **fn sweep_detached** — The rename opens a window a crash can leak a whole task tree into, which is the §2(c) failure the detach is meant to avoid, so construction sweeps it. `.removing-` leads with a dot precisely so `is_task_id` rejects it: a half-removed tree must never read back as a task the listings report.
- **fn admit** — A busy host node is `NoCapacity`, the transient class: spec §3.5 queues and retries it, so no retry budget is spent waiting for the one slot. A hard `Launch` error would fail the job for a condition that clears on its own.
- **fn admit** — The agent test asks what this node **can serve**, never what the launch **declared**, and that follows from placement being per task (#490 D5): the node sees a launch, never a job type, so "this job type was allowed to do this" is not a question it could ask. A missing capability is `Launch` and not `NoCapacity` for the opposite reason the one-slot rule is `NoCapacity` — an absent CLI does not clear by waiting, and queueing on it would spend the whole retry budget on a node that will answer the same way every time.
- **fn admit** — A launch declaring `resources.cpu`/`memory` is a hard `Launch` refusal (job #524, design #309 §7's launch backstop), built from the same `unenforceable_limits` message as the placement filter's pinned case so the two cannot drift. It replaced a `tracing::warn!`-then-run — option 1, the "advisory elsewhere" shape §7 rejects — which P0 reached only because refusing then would have left the prototype nothing to run; `task_timeout` is unaffected and still bounds the task in time, dispatcher-side.
- **fn claude_invocation_path** (`crates/agent/src/claude.rs`) — A launch's `cmd` is the one surface #322 §2's rebase does not reach, so an agent host task's command resolves its own `/chuggernaut` paths through `$CHUG_HOST_CREDS` — the same trick `bootstrap_cmd` plays on the clone destination, one layer up. It routes on the image's presence rather than on a new flag so the composition follows the selector every backend already routes on, which is also what keeps a container's command line identical to the byte.

### `crates/container/src/docker.rs`
- **fn wait** — A non-zero exit surfaces as ContainerWaitError on some daemons — the exit code rides in the error body.
- **fn find_file** — The archive endpoint is the only post-exit read: the container has **exited** by harvest time, so `exec find` is unavailable and resolution streams the directory's tar and reads its headers (design #490 D1a). The stated cost is two node-local passes over a per-task directory — one for the headers, one for the member the copy then fetches — which is the price of not computing an external CLI's directory name.
- **fn archive_matches** — Docker roots every member of a directory download at that directory's own basename, so a match is reassembled onto the caller's `dir` rather than onto whatever the endpoint called the root: the caller gets back a path in the language it asked in, and `copy_file` takes it unchanged. Stripping the root component (rather than trusting it to equal the basename) is also what makes a match structurally unable to name anything outside `dir`.
- **fn remove** — force=false — the caller only removes after the container has exited and its artifacts are harvested.
- **fn remove** — Already gone (404) or a removal already in flight (409): the overlay is reclaimed either way, so removal is idempotent.
- **fn list_managed_running** — One unreachable node must not blank the whole fleet sweep — the others' orphans still get reaped (§3.6).
- **fn fleet_status** — A docker-endpoint node's capacity is static `DOCKER_NODES` config, not an observation: `DOCKER_NODES` remains its owner (design #293 §7), so it reports no capacity and no provenance and the roster's number stands.
- **fn build_host_config** — The KVM device and the read-only toolchain mounts are decided once, from `KvmGrant::admits`, so an edit cannot hand out the wider of the two on its own (design #367 A1). Both of the function's `debug_assert`s pin it by counting read-only mounts rather than testing `mounts.is_some()`, because the cache mount is an independent writable one: the count must equal what the grant declares (the mandatory pair plus one per optional leaf the node provisions — Flutter, the JDK), and the device rides exactly when that count reaches the mandatory pair. Every combination of cache and optional leaves is legal; only "device without the toolchain" is not.
- **fn build_host_config_socket_invariants** — The first `debug_assert` counts the mounts landing at `DOCKER_SOCKET_MOUNT_PATH` on the **built** config through `mounts_target_count`, rather than re-reading the decision that produced them, because "granted nobody" is only checkable on the artifact a launch actually carries. The second states the level half — the socket rides no launch but `CHUG_PHASE=Work`, whatever the allow-list says (design #543 D5) — so a grant that leaked into an evaluator fails a debug build rather than shipping node root to a reviewer.
- **fn build_host_config_socket_invariants** — Root-equivalence is what buys both assertions, and what earned them a helper of their own: the KVM pair guards a wider-than-intended grant, these guard a grant existing at all and a grant at a level nobody consented to. Hoisting them out of `build_host_config` also keeps that function inside the 70-line limit (`docs/reference/style.md` Tier 1) as the socket's invariants grow.
- **fn build_host_config** — Nothing in the tree sets `HostConfig.binds` any more (#379). The field is left at its `Default` `None` rather than removed — it is bollard's struct, not ours — and the dispatcher-side `devices: None, binds: None, mounts: None` invariant is still asserted, so a re-introduced bind fails a test rather than shipping.
- **fn read_only_bind** — `HostConfig.mounts` rather than a `binds` string, because the engine REFUSES a bind whose source is missing while `-v` silently creates it as an empty root-owned directory — measured both ways on `gumbo-nuc-0`, 2026-08-02. Since #379 the sccache mount goes the same way, so a `WORKER_CACHE_DIR` that does not exist fails the launch (`BackendError::Launch`, the engine's message naming the path) instead of yielding an empty directory every task then compiles cold against.
- **fn writable_bind** — Built from `read_only_bind` with the one flag flipped, so `read_only_bind` keeps its read-only-by-construction guarantee (it is unparameterized and cannot be built writable) and both share the missing-source refusal. Two callers are writable and each for its own reason: the build cache, which sccache writes through, so read-only would break it rather than protect it; and the node's docker socket on an allow-listed launch (design #517 D3), which a client cannot connect through when read-only — a read-only bind there would be a grant that reports success and does nothing.
- **fn read_only_bind** — The store is mounted at its own path because the nix-provisioned SDK is a symlink farm whose wrappers name their interpreter and libraries by absolute store path; the SDK mount is not an alternative to it, the two are required together (design #367 correction 9).

### `crates/dispatcher/src/core.rs`

- **fn spawn** — Publish live fleet occupancy once reconciliation settled the running set (re-attached survivors, reaped orphans) — the first snapshot is rebuilt from live containers, not stale state (spec §3.1/§3.6).
- **fn new** — The operator's capacity asks outlive this process (design #293 §4): load them before the first scan tick can reconcile against them.

- **fn on_worker_announce** — Only a fleet-capable backend can route to an announced node. On a single-node Docker deployment (no announcing workers by design) a stray or misconfigured announce would otherwise insert a phantom worker into the roster that nothing can ever route to — and which would then show permanently "down" after the heartbeat scan. - **fn launch** — Drain guarantee (spec §3.1): once the daemon is quiescing for a self-refresh swap, refuse new launches with NoCapacity — a transient* signal the dispatcher queues and retries, so no task fails. The permit is held until the container exists, so the swap never lands mid-launch.
- **fn launch** — The worker runs a single-node local backend; the fleet already chose this node, so no further pin applies.
- **fn logs_tail** — The local backend already caps the chunk at MAX_LOG_TAIL, so the base64 reply fits max_payload — no extra tailing needed here.
- **fn ping** — The pull half of the one capacity source (spec §3.1): the same fields the announce carries, from the same owner. A ping cannot be stale, so this is what makes any ordering anomaly self-healing dispatcher-side.
- **fn refresh** — No git credential ⇒ the refresh would fetch nothing. Report the skip in the reply LOUDLY (spec §3.1 / #114) rather than accepting and no-oping in the background — the deploy then shows the skip instead of a silent "success".
- **fn refresh** — A refresh is already converging — not an error, and not drift: report it as not-accepted so the caller skips the swap-wait rather than logging a scary "not accepted (drift remains)".
- **fn refresh** — Record the accepted refresh as in-progress (ticket #187): a later ping carries this, and `run_refresh` overwrites it with the terminal verdict on failure (a success swaps the daemon away).
- **fn refresh** — Open the live progress record for this refresh (ticket #253) at accept time, so the deploy's very first poll already reads a phase rather than an empty wait. Replaces any previous refresh's record: progress is live state, not history.
- **fn refresh** — The host-work precondition sits before `begin_refresh`, so a refusal costs the node nothing: no build starts and the next refresh finds the slot free. It rides in `skipped` rather than as an RPC error because `skipped` already means "could not even attempt", and the deploy fails the leg for any node that does not print `refresh OK:` either way (design #440 D4).
- **fn host_work_check** — A container node never asks the backend at all: its work is a sibling container that outlives the swap by construction (spec §3.1), so the flag is read before the listing rather than the listing being read and discarded. A listing that FAILS refuses the refresh — a daemon that cannot tell whether a swap would kill a task has only one answer that cannot lose work.
- **fn host_work_refusal** — "Live" is a *running* task, never a launched-and-not-removed one: an exited task's status is already durable on disk (`supervised_cmd` writes it, not the daemon), so a swap under it loses nothing, while the exited-but-unremoved window has no upper bound and would turn one leaked directory into a node that can never be refreshed again (design #440 D4, and job #434's P1 gap list).
- **fn run_refresh** — The host-work re-check runs AFTER the drain wait, not beside it: a launch accepted before `quiesce` may not have created its task directory yet, so the listing is only complete once `drained()` holds. The build phase between the two checks is what makes the second one load-bearing; the drain is what makes it correct.
- **fn run_refresh** — Cancellation is checked BEFORE the build's own verdict: a cancel kills the build, so the build error it produces is a CONSEQUENCE of the cancel, not the cause. Attributing it to `build` would put "the node's build broke" in a deploy leg for a node the deploy itself stopped (ticket #254).
- **fn run_refresh** — Drain guarantee: refuse new launches, then wait for accepted-but-not-yet- created launches to finish before swapping (spec §3.1).
- **fn run_refresh** — Last cancellable instant: past `begin_swap` the node is going onto the new images and a cancel is refused, so this is where a cancel that arrived during the build or the drain actually stops the refresh.
- **fn run_refresh** — The swap spawns a detached replacement, so on success this process is simply removed and never returns here. Reaching this arm means the swap itself failed to launch — reopen so the node keeps serving.
- **fn record_refresh_failure** — `error` already carries the script's captured tail on a build/swap failure; bound it the same way the daemon streams so the ping reply and the durable outcome stay small.
- **fn refresh_cancel** — Only OUR target may be cancelled: a node converging on some other SHA (a concurrent deploy, a hand-run refresh) is none of this deploy's business.
- **fn run_script_stream** — Feed both streams' lines into one channel; a single consumer prints and buffers them so stdout/stderr interleave in arrival order.
- **fn run_script_stream** — Keep only the last REFRESH_TAIL_LINES lines so a long build log stays memory-bounded; each line is streamed out immediately as it arrives.
- **fn nix_roots** — A declared roots dir absent from the daemon's own view refuses the boot, the same shape a declared KVM device gets and for the same reason: the alternative is realising nothing, per task, silently — which reads as "GC roots are on" while every closure a task holds stays collectable. The toolchain is checked alongside it on a node that attaches a device, and the property checked is that it RESOLVES INTO THE STORE rather than that it exists — existence is precisely what a mount of the wrong path satisfies while every admitted launch fails.
- **fn spawn_nix_reaper** — A pass that cannot see the node's containers is SKIPPED, never reaped on: an empty live set would look exactly like a node with no work and would pull the roots out from under every running task. The tracked-root union covers the other direction — a launch whose container the node cannot see yet — and the interval's immediate first tick is spent doing nothing, because a daemon still booting has neither tracked roots nor a settled docker connection.
- **fn reap_live_tasks** — The count is asked for BEFORE the listing purely because of which one propagates an error: `DockerBackend::managed_running_total` fails the whole count when a node cannot be reached, while `list_managed_running` warns and returns an empty vec, so gating on the listing alone would have read "nothing is live" and reaped every root over the grace period.
- **fn realise_for_launch** — The realise happens BEFORE the container exists, so a failure here has no task to fail: it fails the launch, and the reservation the dispatcher holds is released by the launch's own error path.
- **fn remove** — The root is released whatever the removal did. The task is over either way, and `dispose` is best-effort by design, so a removal error must not strand the pin it was going to drop.

### `crates/worker/src/route.rs`
- **struct RoutedBackend** — Exists only on a node whose `WORKER_MODES` names both runtimes (design #309 §1), which is why a single-mode node holds its one backend directly and is unwrapped: the type is the routing, so a node with nothing to route between must not pay for it. The launch routes on the image's presence and every later op on the id the launch minted (`container::host::names_host_task`), because after the launch the request no longer carries a mode and the id is the only thing that knows which backend owns the work.
- **fn list_managed_running** — The union of both backends, not the docker one: a dual-mode node's occupancy is the node's, and the ping count, the §3.6 sweep and the nix reaper all read it. A host task missing from that set would read as a free slot on a node whose whole capacity rule is that it has one.

### `crates/worker/src/nix.rs`
- **struct NixRoots** — The client is a PROFILES path, not a store path, and that is the whole trick: docker resolves a bind source host-side at create, so a store-path client would be pinned to the generation current when the long-lived daemon was last swapped, and `--delete-older-than` collects old generations. `/nix/var/nix/gcroots/profiles` is itself a root, so resolving through the profiles at each use follows the node's current generation.
- **fn store_target** — Shared by the boot check and the launch so one property is stated once: the client canonicalizes `--realise`'s argument in its own namespace, so a bind whose source is the operator's stable path hands it the store path's content at a non-store path, which nix refuses with `BadStorePath`. Binding the parent instead keeps the symlink readable and shared, so a `nixos-rebuild` moves the toolchain under a running daemon rather than pinning the generation current at the last swap.
- **fn realise** — `kill_on_drop` is what makes the bound real: dropping the timed-out future kills the client, so an over-bound realise cannot leave a process running against a launch that has already been refused. The nix daemon's own build continues — the bound is on the worker's wait, not on the node's builder.
- **fn finish_realise** — A client that exits 0 without writing the root is treated as a failure, not a success: the launch would otherwise proceed against a closure nothing pins, which is the exact hazard the root exists to close.
- **fn check** — Every precondition is checked in the DAEMON's view rather than the node's, because a containerized daemon has neither by default; the toolchain path is there for a subtler reason than the other three, since `--realise` resolves it client-side before the socket is opened, and nothing else in the launch path would have noticed it missing until the launch failed.
- **fn reap** — Best-effort in every arm (design #373 Decision 4): an unreadable directory, an unstattable entry and a failed unlink each leak disk and none of them reaches a job. The age floor is the second half of the safety argument — a root younger than it may belong to a launch still in flight.

The fields already render these messages — the banner only says where.

### `web/src/pages/Project.tsx`
- **const FILTER_STATES** — The states the state-filter dropdown offers, lifecycle-ordered. The default ("Active") is no filter at all — the finished-hiding gate in matchesFilters is what makes the unfiltered view active-only, and "All" is that same gate lifted.

Deliberately not what the cell shows — the gap between this and the task time below is the queueing and waiting the job did while Frozen and Blocked. Undefined for live jobs so the cell has no tooltip.
- **function taskTimeHint** — The completed cell's muted hint: how long the job spent *working* — the sum of its own tasks' spans, carried on the jobs-list record (`task_time_ms`) so the table reads it straight off the row instead of fetching tasks per job. - **function oneLine** — Collapse a channel message to a single line for the muted under-title glance (the full multi-line text rides in the tooltip). Runs of whitespace — including the newlines in markdown prose — become single spaces.
- **const CHANNEL_STATES** — Jobs whose latest channel-update is worth surfacing under the title: the two live, agent-driven phases. Evaluation shares Work's channel stream, so it costs nothing extra to include (per the brief).

Alphabetical scatters related states, so rank them by lifecycle instead: inert pre-release first, terminal history next, live activity, then attention-needed at the very end — so the default descending click surfaces Escalated/Failed on top and sinks Frozen/Revoked to the bottom. Unknown/future states rank after everything (RANK_UNKNOWN) and still render their name as-is.

So type into local state and push to the URL once typing settles. `qPending` also tracks what we last wrote, so the sync below can tell a URL change we caused from one we didn't (back/forward, a shared link) and only adopt the latter.
- **function ProjectPage** — Seed/refresh the progress lines from the list. A live SSE event is always newer than the snapshot it raced, so let the existing ts guard decide rather than clobbering: only fill in what we don't already hold at an equal-or-newer stamp.
- **function ProjectPage** — Best-effort capacity-queue snapshot (spec §3.5): the seqs with a launch waiting for a fleet slot, for the subtle "queued" chip. Never blocks the list — an unreachable dispatcher just drops the chip.
- **const channelMsgs** — Latest channel-update message per job, surfaced muted under the title for live jobs. Seeded from the jobs list itself (each live job carries its latest post), then kept current from live SSE events. It used to be seeded from the SSE history replay, which meant every page load downloaded the project's entire event history — ~900 KB to annotate a handful of rows. Reset on project change so stale rows don't bleed across navigations.
- **const debouncedRefresh** — The SSE stream is the source of truth (Part 11): any event → refetch. On page load the stream replays the full history, so debounce to collapse that burst (and any live burst) into a single refetch.
- **const fleetTick** — Live fleet capacity readout (#148). Every occupancy change rides a task lifecycle event already on this stream, so bump a tick (debounced against the load-time replay burst) to refetch the snapshot. Admin-only feed: the widget hides itself when unavailable. The tick only fires on *this* project's events, but the fleet is shared across projects (#177) — so also poll on an interval, catching a sibling project's occupancy changes and the end-of-burst quiescence after which no further event fires. Same-project activity still updates instantly.
- **const onEvent** — Every event both feeds the debounced refetch and, when it's a channel-update, updates the latest-message-per-job map. Guard on ts so an out-of-order frame can't overwrite a newer message with an older one.
- **const depGate** — Release readiness of a Frozen job's deps, resolved client-side from the same jobs fetch (the list already holds every job). Releasing before every dep is Done is at best a Blocked transition; a dep that is Revoked/Failed can never satisfy it, so the job is un-runnable. Gate the run button accordingly and surface which deps are the holdup instead of silently offering a bad action.
- **const claimedInWork** — Jobs whose Work attempt is parked for a human (a claim materialized: a human is doing the work locally, no agent launched). No extra fetch, no API change: `claim_next` covers the pre-park window, this covers the in-Work window, so the claimed badge persists for the whole life of the claim.
- **const inbox** — A terminal job's pending tasks are zombies — revoke doesn't (yet) close them out server-side, and there is nothing valid to resolve. Hide them so the inbox never offers actions the dispatcher will reject.
- **const askKind** — What the card is asking of the operator — the resolution vocabulary differs (escalations take retry/resolve/revoke, the rest pass/fail).

- **const byId** — Group batch members under their batch so they always travel as one unit: while a batch is on screen its members never float free in the list — they render indented directly beneath it, and only when the batch is expanded (members come from the full jobs list, so expanding shows all of them even if the current filter would hide Batched rows). - **function ProjectPage** — What the job is part of (design #321). In the title cell rather than a column of its own: the table has no width to spend on an eighth column, and on a phone the title cell claims the whole line, so the chips wrap under the title instead of squeezing the metadata line.
